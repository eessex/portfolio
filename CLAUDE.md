## Commands

```bash
pnpm dev             # start dev server (turbopack) on localhost:3000
pnpm build           # production build
pnpm lint            # eslint .
pnpm typecheck       # tsc --noEmit
pnpm prettier        # prettier --write .
pnpm test            # jest
pnpm test:watch      # jest --watch
pnpm test:quiet      # jest --silent --noStackTrace (summary output only)
pnpm run setup       # interactive first-run setup: .env, DB schema (writes to the real DB); claim the admin account at /setup
pnpm migrate         # apply pending migrations + every-deploy steps to the DB .env points at (writes to the real DB)
pnpm run copy-storage --to <provider> [--dry-run]       # copy stored files between providers (writes to storage + DB)
pnpm run backfill-image-variants [--prune] [--dry-run]  # write missing/outdated image variants (writes to storage + DB)
pnpm run migrate-mongo --input <dir> [--dry-run]        # one-off import of the old site's Mongo exports (writes to the real DB)
pnpm run reset-password <email> [--url <site>]           # print a one-time reset link for a locked-out admin (writes to the real DB)
```

Run a single test file: `NODE_OPTIONS=--no-deprecation jest src/lib/releases/data.test.ts`
Run a single test by name: add `-t "test name"`.
Jest treats a path argument as a regex, so escape parentheses in route-group paths or the file silently won't match: `jest 'item-pages\)/item-layout'`, not `jest "src/app/(item-pages)/item-layout.test.tsx"`.

When running commands agentically, keep output minimal: prefer the single-file jest invocation (with `--silent`) while iterating and `pnpm test:quiet` for full-suite checks; drop the flags only when a failure needs its console output or stack trace. Don't run `pnpm build` unless the task specifically requires verifying the production build — `pnpm typecheck` + `pnpm lint` cover correctness checks.

Package manager is pnpm (`packageManager: pnpm@11.0.0`); Node 22.x. CI is split: GitHub Actions (`.github/workflows/checks.yml`, source repo only) runs typecheck → lint → test:quiet on PRs and pushes to `main`, and Vercel's build command (`vercel.json`) is `pnpm migrate && pnpm build`, so a failing migration or build fails the deploy. `pnpm check` still runs typecheck → lint → test:quiet → build locally. Migration-writing rules are in `CONTRIBUTING.md`.

## Architecture

This is a Next.js 16 (App Router, `cacheComponents` enabled) CMS for a personal portfolio site, backed directly by Postgres (Neon serverless) with no ORM — all queries are hand-written tagged-template SQL via the `sql` client in `src/lib/db.ts`.

### Domain module layout

Each content type (`releases`, `events`, `projects`, `venues`, `links`, `images`, `embed-codes`, `published-editions`, `publishers`, `site-settings`, `users`, `email-subscriptions`) lives under `src/lib/<domain>/` with a consistent file split:

- `data.ts` — raw read queries: single-item `fetch*ById` and the uncached list query `fetch*Raw`. It never imports `cached.ts` (that would be a cycle)
- `cached.ts` — the list entry point `fetch*` (first page with no query → its cached `fetchCached*FirstPage`; later pages and searches → `fetch*Raw`, uncached), which API routes and dashboard pages import from here, plus `'use cache'` wrappers around `data.ts` reads, tagging each read with its domain's base tag (`releases`) plus, for a single item, its own `<singular>:<id>` (`release:<id>`; a release/event read also carries its embedded project's `project:<id>`), which `updateTag` in `actions.ts` invalidates. Cache keys already include the arguments (e.g. `isAuthed`), so there are no per-variant tags; don't add a tag nothing invalidates
- `actions.ts` — `'use server'` mutations (create/update/delete), calling `updateTag(...)` after writes
- `schemas.ts` — Zod schemas per domain (often split into `schemas/db.ts` / `schemas/client.ts` for larger domains), built from shared primitives in `src/lib/schemas/primitives.ts` and fields in `src/lib/schemas/fields.ts`
- `types.ts` — types inferred from schemas
- `fixtures.ts` — test fixture builders
- `util.ts` — domain-specific helpers (e.g. `sortReleasesByCategory`)

`src/lib/schemas/index.ts` defines the two cross-cutting taxonomies: `pagePaths` (content types with their own public `/​{path}` and `/{path}/{slug}` pages: events, projects, releases) and `embeddedItemTypes` (items with no own page, embedded into pages and reusable across them: embed codes, images, links, published editions, publishers, venues). Published editions are the exception to "reusable": each belongs to one release and is edited only inline from its form (see "Releases and published editions"), so `dashboardItemTypes` (the admin menu's Library group, whose list pages offer "New {type}" in their `DashboardLayout` header) leaves them out.

### Project ownership of page items

`releases` and `events` each carry a `project_id` FK (indexed) to the project they belong to (a published edition's project is its release's); it's a real filter (`/api/releases?projectId=`, a project page's release/event tables). On releases it's `NOT NULL` (`ON DELETE RESTRICT`), required by `releaseSchema` and the release form. On events it's nullable (`ON DELETE SET NULL`), and `NULL` means the event belongs to no specific project. `deleteProject` hands the project's releases/events to the default project (`handOffPageItems`) before deleting, in one transaction, since the releases FK would otherwise block the delete and the events FK would leave them unowned. If the project has releases and no default project exists, `deleteProject` returns a form error instead.

Images, links and embed codes have no owner: a project lists them through its own `image_ids`/`cover_image_id`/`link_ids`/`embed_code_ids`, and the dashboard's "Used on" `project_slugs` is derived from those arrays, like `event_slugs`/`release_slugs`. They have no `project_id` column. Because saving a project changes which projects list an item, and can also create images/links/embed codes inline (via their item pickers' create-new flows), `invalidateProjectTags()` invalidates the `images`/`links`/`embed-codes` cache tags too, not just `projects`.

### Default project and `/about`

One project row may carry `is_default_project = true` (a partial unique index allows at most one; a second insert is caught and returned as the form error "A default project already exists"). It is the site's own project: `/about` renders it through the shared `ItemLayout` (`fetchDefaultProject`/`fetchCachedDefaultProject`, tags `projects` and `project:<id>`), with a published-first lookup that only reads the session when an unpublished default exists, so the page stays static for anonymous visitors. `/about/edit` edits or creates it via `EditProjectForm isDefaultProject` → `editDefaultProject()`, the only action that sets the flag; updates never change it (`toDbRow` keeps the stored value). It can't be deleted: `deleteProject` checks the stored flag server-side and returns a form error, and the Delete button is hidden wherever it's edited. Where it's listed (project pickers), it comes first, on the first page only (later pages' cursors skip it), like the built-in publisher. Project indexes leave it out via `isDefaultExcluded` (`fetchProjects` option, `/api/projects?isDefaultExcluded=true`, `ItemsTable` `searchParams`). On `/about` the layout differs only in its header (passed through `ItemLayout`'s `header` slot, which replaces the default category/title/date/venue header and switches to the minimal left-aligned layout: just "About" plus a draft badge) and its children: a `ProjectsCarousel` of the other projects, and no event/release tables. `/about` isn't a `pagePaths` entry; it 404s until a default project exists (or, for anonymous visitors, while it's unpublished), the default project's own `/projects/<slug>` (and `/edit`) redirect to `/about` (and `/about/edit`), and `itemUrl()` links it there. The old `about` table may still exist in provisioned databases, but nothing reads it and the baseline migration doesn't create it. Event and release forms don't preselect a project: the Project picker starts empty (or with the item's own project). Existing unowned releases/events were backfilled to the default once, and `deleteProject` hands off to it, so new `NULL`s come only from creating an event with no project (or a direct DB delete of its project).

### Data flow conventions

- DB rows are `snake_case`; client-facing objects are `camelCase`. `formatDbResponseForClient()` (`src/lib/util.ts`) converts via `camelizeKeys()` (`src/lib/strings.ts`), turns `null` into `undefined`, and validates/parses through the domain's Zod schema — always route raw SQL results through this before returning them.
- List endpoints use cursor pagination: `encodeCursor`/`decodeCursor` base64-encode `{ name, id }`, `formatResponseWithCursor()` builds the page + `nextCursor`, page size is `DEFAULT_PAGE_SIZE` (24). The list-fetch frame (total count → decode cursor → page query → format + `totalCount` merge, with per-query labelled errors) is implemented once by `runListFetch()` in `src/lib/list-fetch.ts`; a domain's `fetch*Raw` supplies only its `count`/`list` tagged-template SQL callbacks (receiving `like`, `cursorName`, `cursorId` and the full decoded `cursor`), `cursorKey`, schema, and an optional `transform` for grouped page responses (e.g. `sortEventsByCategory`). The count query always runs before the page query — tests mock `sql` and rely on that order.
- Server actions (`actions.ts`) receive `FormData`, run it through `normalizeFormData()` (checkbox `'on'` → `true`, empty strings → `undefined`, blank `*Date` fields → `undefined`), then `schema.safeParse()`. Failures return `formatValidationResponse()`; thrown DB errors are caught and returned via `formatErrorResponse()` — actions return a `FormResponse<T>` (`{ ok: true, res }` or `{ ok: false, message, errors? }`) rather than throwing, so UI forms can render field errors inline. This frame (auth check → normalize → validate → save → invalidate tags → format errors) is implemented once by `runFormAction()`/`runDeleteAction()` in `src/lib/form-action.ts`; a domain's `actions.ts` supplies only its schema, message label, SQL `save`/`del` callbacks, and cache invalidation (plus optional `prepare` for pre-validation work like file uploads — a thrown `prepare` error is caught and returned as a normal `{ ok: false }` form error rather than a rejected action — and `isNormalized: false` for schemas validating raw entries). `form-action.ts` also exports `saveItemFromFields()`, the same normalize → validate → create-or-update pipeline for a single item saved from raw fields (not `FormData`) rather than its own form submit — used when an item picker's inline "create/edit" entry saves an embedded item as part of another domain's mutation. It also exports the two picker resolvers those entries go through: `resolveItemId()` (one single-item entry → an id) and `resolveOrderedIds()` (a multi picker's entries → ordered ids), each taking only the domain's `save*FromFields` callback, so a domain's `resolve*Id`/`resolveOrdered*Ids` is a thin wrapper that adds just its own return shape (e.g. the cover-image split).
- Embedded items can be created or edited inline from within another item's form via `ItemPicker` (`src/ui/item-picker/item-picker.tsx`) — see "Embedded item pickers" below. On the server, `extractIndexedGroups()` (`src/lib/util.ts`) parses the resulting indexed form groups (`${prefix}[0].field`, ...) into `existing` (untouched selection, just an id), `edited` (an id plus changed fields — an existing item opened and edited inline), or `new` (no id — a pending creation) entries, preserving submission order since some callers derive meaning from position (e.g. "the first entry is the cover image"). Field names may be nested paths (`publishedEditions[0].publisher.name` yields field `publisher.name`), for a picker nested inside another's entry. `extractPrefixedGroup()` is the single-item counterpart, classifying one entry (`venue.city` + `venueId`) the same three ways; it sweeps every key under the prefix rather than a per-domain field list, so nothing a form submits is left behind for the parent schema and no domain has to guess which of its fields prove an editor was open.
- Auth-aware reads take an `isAuthed` boolean to decide whether unpublished (`is_published = false`) rows are included; API routes and pages pass this from `isAuthed()` in `src/lib/auth/guard.ts`.
- Auth guarding (`src/lib/auth/guard.ts`): every `'use server'` mutation is session-checked before any work — form mutations get this from `runFormAction()`/`runDeleteAction()` (which call `requireAuth()` first); bespoke actions call `requireAuth()` (returns a `FormResponse` error to return early with) or `assertAuthed()` (throws, for exposed functions that don't return `FormResponse`, e.g. `uploadFile`/`deleteImageFile`) directly. This is required because middleware only protects page navigation — server actions are invoked by action id and can be POSTed to any public route. Reads are deliberately public through pages and the embedded-item `/api/*` routes, which take no session since embedded items have no publish state. `data.ts` fetchers are plain server modules, not `'use server'`, so they aren't callable as actions; a client component that needs a read calls a session-checked wrapper in its domain's `actions.ts` instead (e.g. `findSocialLink`). The only deliberately public actions are `authenticate`, `createEmailSubscription`, `completeSetup`, `recoverAccount`, `acceptInvite` and `resetPasswordWithLink` (see Auth below for the last four). Tests get an authed session by default from the `@/auth` mock in `src/test/jest.setup.ts`.
- Postgres schema comes from versioned migrations in `migrations/` (`NNNN_short_name.sql`, or `.ts` only when SQL can't express it, with no app imports), applied by `pnpm migrate` (`scripts/migrate.ts`, logic in `scripts/migrate/runner.ts`): each file runs once per database, in order, in its own transaction, under an advisory lock on the direct (unpooled) connection, and is recorded in `schema_migrations` with a checksum, so a shipped migration is never edited (the next run fails on it); a change is always a new file. `0001_baseline.ts` is the frozen schema from before migrations (all `IF NOT EXISTS`); check it plus later migrations when the on-disk schema of a table needs to be understood. After migrations, the runner re-runs the every-deploy steps in `src/seed/every-deploy.ts` (their SQL follows the code): `syncCheckConstraints()`, which deliberately rebuilds each enum-like CHECK (listed in `checkedColumns`: project/image/link/publisher/release types, embed code type/host/content type, edition format, user token purpose) from its code constant whenever its values differ, so a value added in code needs no migration and value lists never go in a `CREATE TABLE`; the slug history function and triggers (a trigger is recreated only when it doesn't match, and a CHECK only when it differs, since both lock their table); the JSONB builder functions; the built-in publisher seed; `ensureAuthSecret`, which inserts a random `auth_secret` row into `instance_secrets` (migration `0002`) once and never rotates it (an `AUTH_SECRET` env var still wins when set — see Auth below); and `ensureSetupCode`, which while `users` is empty keeps a still-live `setup_code` row (migration `0004`) or mints a fresh one, and deletes it once a user exists (see Auth below). Changing any of their SQL (a new enum value included) means bumping `EVERY_DEPLOY_REVISION` in `every-deploy.ts`, which `every-deploy.test.ts` pins to a checksum of the SQL; the runner records it in `schema_every_deploy` and refuses a checkout with a lower one, like a checkout missing applied migrations. The steps and that revision write run in one transaction. It and each transactional migration run with a short `lock_timeout` (under the 1s `deadlock_timeout`, so the runner, not a live query, gives way in a lock-order cycle), retried whole on a lock timeout or deadlock; a `-- migrate:no-transaction` file isn't retried, since its statements commit one by one. `migrations/` is in `.prettierignore` so formatting never changes a shipped file's checksum. Ship the code that stops reading/writing a column at least one release before the migration that drops it (expand → switch → drop across three releases), since the previous release's code stays live while a build runs and after a rollback.
- First-run/local setup (`.env` creation, `AUTH_SECRET` generation, `DATABASE_URL` prompt + connection test, migrations via the same runner as `pnpm migrate`) is handled by `scripts/setup.ts` (`pnpm run setup`); every step checks current state before acting, so it's safe to re-run against an already-provisioned instance. It doesn't create an admin itself — migrating prints a setup code the same way a deployed build does, except that it passes `isSetupCodeRotated` (an `EveryDeployOptions` field, threaded through `migrateDatabase` → `runMigrations` → each step) so `ensureSetupCode` replaces a live code instead of keeping it (only the hash is stored, so a lost code can't be reprinted); the rotation runs inside the every-deploy transaction, after the runner's skip/refusal checks, so a skipped or refused run keeps the old code, and the first admin is always created at `/setup` (see Auth below), through `src/lib/users/create.ts`'s `createFirstUser()`, so there's one admin-creation path, not a CLI one and a web one to keep in sync. `createUser()` beside it stays a plain, unconditional insert (unused: invited admins go through `createInvitedUser()`), and is deliberately _not_ a `'use server'` action (only callable from server-side scripts).

### Embedded item pickers

`ItemPicker` (`src/ui/item-picker/item-picker.tsx`, backed by `Combobox` in `src/ui/combobox/combobox.tsx`) is the shared control for attaching embedded items (or, for reusable page items like projects, page items) to a form: search-and-select an existing item, or create a new one inline without leaving the parent form. Each open entry (`ItemPickerEntry`, `src/ui/item-picker/item-picker-entry.ts`; validated by `useEntryValidation` in `use-entry-validation.ts`) is either an existing selection, a new item being drafted, or an existing item opened for inline editing; a completed entry collapses into a chip (`renderExistingResult`) rendered via `SelectedResult`, and reopens back into its editor (`renderEditItemForm`) on click. Supports single (`isMulti: false`) or multi-select with drag reordering (`SortableList`); list order alone decides what renders first. It opens on a blank create form unless `isSearchFirst` is set (venues, publishers — types whose first field is free text the search box can capture). With `isCreatedFromQuery` (publishers), a search-first picker's results end with a "Create “{query}”" option instead of a New button, creating the item from the query alone and collapsing it straight to its chip. `isSearchHidden` (multi only; published editions) is create-only: no search, a New button, and a blank editor only while the list is empty; as in every picker, Cancel appears only when editing an existing item, not on new drafts. Button and search text derive from the item type (`New link`, `Search links`); `itemName` and `searchLabel` override them where one item type is picked for a narrower purpose (`PressLinksPicker`: "New press link", "Search press links", with the press badge hidden via `formatLinkResultWithoutBadge`). Domain edit forms passed as `renderEditItemForm` (e.g. `EditEmbedCode`, `EditImage`, `EditLink`, `EditPublisher`) follow a progressive-disclosure pattern — starting minimal (e.g. just a paste-a-URL field) and revealing the rest of the fields once the pasted value resolves, through `useDisclosureDetails`/`DisclosureDetails` (`src/ui/form/disclosure-details.tsx`), whose `disclosure-details` fieldset is what the picker boxes a draft around — and report readiness/in-flight state back to the picker via `onReadyChange`/`onBusyChange` so it can gate Save on async work (e.g. resolving embed code oEmbed metadata) finishing first.

An entry's fields are namespaced so the parent form's own fields can't collide with them, and the namespace is never passed as a prop: both sides derive it from `src/lib/item-fields.ts`, a dependency-free module shared by the client that renders the fields and the server that reads them back. `itemIdFieldName(itemType, name)` gives the hidden id input's name (`name` if given, else `${singular}Id`) and `itemFieldPrefix(idFieldName)` turns that into the namespace by dropping the `Id` suffix (`venueId` → `venue.`, `coverImageId` → `coverImage.`), so two pickers of the same item type in one form stay distinct as long as their id fields do; `indexedItemFieldPrefix(name, index)` is the `isMulti` counterpart (`images[0].`, where a multi picker's `name` defaults to its `itemType`), matching what `extractIndexedGroups()` parses, alongside `emptyListFieldName(name)` for a multi picker's empty-list marker. The picker provides the derived prefix through `NamePrefixContext` (`src/ui/item-picker/name-prefix.tsx`); edit forms read it with `useNamePrefix()` and prefix every input `name` with it, which yields the bare names they need when rendered outside a picker (the `/dashboard/*` edit pages) since there's no provider there. A picker rendered inside another's entry prepends that outer prefix to its own field names (`publishedEditions[0].publisherId`, `publishedEditions[0].publisher.`). Server-side, `extractIndexedGroups()` strips the indexed form and `extractPrefixedGroup()` the single one; the `resolve*Id` helpers (`resolveVenueId`, `resolvePublisherId`, `resolveCoverImageId`) each take the _id field name_ as their argument (defaulting to what the picker derives) and hand it to `resolveItemId()`, which derives both the id key it reads and the prefix it strips from that one name. All three submission shapes — an untouched existing selection (id alone), an existing item edited inline (id + fields, UPDATEd), and a pending inline creation (fields alone, dropped when blank) — are therefore handled in one place rather than per domain.

### Releases and published editions

Releases are created and edited at `/releases/new` and `/releases/<slug>/edit` through `EditReleaseForm` (`src/ui/releases/edit-release-form.tsx`) → `editRelease` (`src/lib/releases/actions.ts`). A release's published editions are child rows (`release_id NOT NULL`, `ON DELETE CASCADE`) edited only through the release form's create-only editions picker; there is no edition dashboard or `/api/published_editions`. `editRelease` reads the picker's entries (`extractPublishedEditionEntries` in `src/lib/published-editions/util.ts`; `undefined` when the picker wasn't submitted, which leaves editions alone), requires at least one, and validates each against `publishedEditionDraftSchema` (which also requires a `publisherId` or inline `publisher.name`) _before_ writing anything. It returns failures as a `publishedEditions` field error. `release_date` has no input: it's derived as the earliest edition's `publish_date` (untouched editions are read from the DB, scoped to the release). After the release row is saved, `syncReleasePublishedEditions` creates new editions, updates edited ones (UPDATE scoped to `release_id`), and deletes the release's editions no longer listed. It isn't one transaction (Neon HTTP can't interleave logic), hence the up-front validation. If the sync still fails, it deletes the editions it just created, and `editRelease` deletes a newly created release row (so a resubmit doesn't duplicate it) or, on an update, re-derives the already-saved release's date from its surviving editions and invalidates its tags before returning the error. Editions' `buy_link_id`/`image_ids`/`cover_image_id` columns are no longer read or written; they stay in the table only until a migration drops them. Inline publishers are created from a name alone and edited as name + website (`EditPublisher isTypeHidden`; `publishers.type` is nullable) and reuse an existing publisher with the same name, case-insensitively (`findOrCreatePublisher`).

One publisher is built in: the every-deploy seed (`src/seed/every-deploy.ts`, run by every `pnpm migrate`, setup included) inserts the "Self-released" row (`SELF_RELEASED_PUBLISHER_NAME`) with `is_built_in` unless a built-in row exists; a partial unique index allows only one. It's listed first in publisher results (first page only, so the name cursor of later pages skips it), and it's read-only: `updatePublisher`/`deletePublisher` refuse it by its stored flag, its dashboard edit page shows a notice instead of the form, and the edition form's publisher chip offers no Edit (`ItemPicker` `isItemEditable`).

A release's `artist` is saved on the release, a snapshot so renaming a project never re-credits past releases. The form's Artist field is required and auto-filled with the selected project's name, following the project picker through `ItemPicker`'s single-picker `onSelectionChange` while the value is blank or still the auto-filled name; a typed name (e.g. "Joe Smith & Friends") is kept. Server-side, `resolveArtist` still saves the project's current name for a blank artist, as a fallback. The release fetches also return `display_artist` (`COALESCE(r.artist, project title)`), which `formattedItemTitle()` and other displays use, as a fallback for older rows with no artist.

### Auth

next-auth v5 with a `Credentials` provider (`src/auth.ts`, bcrypt password check against `src/lib/users/data.ts`). Route protection is centralized in `src/auth.config.ts`: `authedPathPatterns` (derived from `pagePaths` for `/*/new` and `/*/:slug/edit`, plus `/about/edit` and `/dashboard/*`) `unauthedPathPatterns` (`/login`, `/forgot-password`) and `linkPathPatterns` (`/invite`, `/reset-password`: reachable signed in or out, and before site settings exist), defined in the client-safe `src/lib/auth/paths.ts`, are checked in the `authorized` callback; everything else is public. Vercel Analytics and Speed Insights (`src/ui/analytics/analytics.tsx`, in the root layout) drop events on all three sets of paths via `beforeSend`, so only public traffic is counted. `src/proxy.ts` wires this config into the Next.js middleware matcher. Both `src/auth.ts` and `src/proxy.ts` use NextAuth's lazy config to supply `secret` from `authSecret()` (`src/lib/auth/secret.ts`): the `AUTH_SECRET` env var when set, else the instance's generated `instance_secrets` row, read once per server instance and never replaced by a random fallback (a missing secret throws). The `authorized` callback checks three states in order, each memoized in module state once true the same way (an in-memory flag, not cached per-request, so neither check pays for a DB round trip on every anonymous page view once it's settled; a transient DB error fails open — treated as the later/safer state — rather than taking down every public page): no admin exists yet (`anyUserIsCreated()`, backed by `hasUsers()`) — every path redirects to `/setup` except `/setup` itself, since nobody could be logged in either way; an admin exists but `site_settings` doesn't (`siteIsConfigured()`, backed by `hasSiteSettings()`) — logged-out visitors are gated to `/login`; configured — the authed/unauthed-path behavior above.

Sessions are JWTs, so ending them works through `users.session_version` (migration `0005`): `authorize()` copies it into the token (and stamps `last_login_at`, via `recordLogin()`, which only matches while the row still has the version the password was checked against, so a change landing mid-login fails that login rather than handing old credentials a current token), and the `jwt` callback (`checkSessionVersion` in `src/lib/auth/session-version.ts`, wired in the shared `authConfig`, so both `src/auth.ts` and `src/proxy.ts` run it) re-reads it on each `auth()` call that carries a session token (deduped per request with React `cache`) and returns `null` on a mismatch or a deleted user, so bumping it signs that account's sessions out at their next navigation or `requireAuth()`/`isAuthed()`; in the proxy a `null` also clears the session cookie, so a revoked session can reach `/login` again. A token with no version counts as `0`, and a failed lookup fails closed (the session ends, so a revoked token can't pass during a DB outage). The `session` callback (`withUserId`, same file, also in `authConfig`) adds `session.user.id`, read by `currentUserId()` in `guard.ts`.

The signed-in admin's own account is edited on `/dashboard`, in accordions below the site settings (`NameForm`/`EmailForm`/`PasswordForm` in `src/ui/users/account-forms.tsx`; one per accordion so only one current-password field shows at a time; their own `Suspense`, since they read the session) through `changeName`/`changeEmail`/`changePassword` in `src/lib/users/actions.ts`, whose SQL is in the non-action `src/lib/users/update.ts`. Email and password changes require the current password, checked under the login throttle (`registerLoginAttempt` keyed by the account's email), bump `session_version` in an UPDATE conditioned on the version read before the password check (`updateUserPassword`/`updateUserEmail`; no row matched means a concurrent change won, returned as a form error), then call `signIn('credentials', { redirect: false })` so this device gets a fresh token while every other session ends. New passwords, `/setup`'s first one included (`completeSetupSchema`), are entered through `NewPasswordInputs` (`src/ui/users/new-password-inputs.tsx`) and use `newPassword` from `src/lib/users/schemas.ts` (`MIN_PASSWORD_LENGTH` 15 to `MAX_PASSWORD_LENGTH` 64, per NIST SP 800-63B, and at most `MAX_PASSWORD_BYTES` 72 UTF-8 bytes, bcrypt's input limit) and `isPasswordBreached()` (`src/lib/auth/breached-password.ts`: the Pwned Passwords range API, sending only a 5-character SHA-1 prefix, with padding, failing open). Login, `userSchema` and the DB check still accept 8+ so existing passwords keep working.

Recovery codes (`user_recovery_codes`, migration `0006`) let a locked-out admin reset their password without email: `RECOVERY_CODE_COUNT` (8, in the client-safe `src/lib/users/schemas.ts`) codes per set, 10 Crockford Base32 characters each (`generateRecoveryCodeSet()` in `src/lib/auth/recovery-codes.ts`, built on `generateGroupedCode`/`normalizeGroupedCode` from `src/lib/auth/grouped-code.ts`, which `setup-code.ts` shares), stored only as bcrypt hashes; their SQL is in the non-action `src/lib/users/recovery-codes.ts`. The first set is inserted by `createFirstUser()` in the same statement as the account, and `completeSetup` signs in with `redirect: false` and returns the plain codes, so `SetupForm` shows them (`RecoveryCodesList`, `src/ui/users/recovery-codes.tsx`, whose Continue waits for an "I've saved these" tick) before pushing to `/dashboard`; `Form`'s `onSuccess` receives the action's `res` for this. The dashboard's Recovery codes accordion (`RecoveryCodesForm`) shows how many are left and swaps in a new set through `regenerateRecoveryCodes` (current password required, login throttle; `replaceRecoveryCodes` locks the users row in a transaction so a double submit can't leave two sets live, and writes only if `session_version` still matches the one read before the password check, else `STALE_RESPONSE`). `/forgot-password` (an `unauthedPathPatterns` entry, linked from `/login`) posts to the deliberately public `recoverAccount`: validate → `checkWindowLimit` keyed `recover:<ip>` (each attempt runs a full set of bcrypt compares, and the email throttle is dodged by varying the email) → breached check (before the code and the email throttle, so a rejected password neither uses a code up nor counts as a failure) → login throttle keyed by the email → `fetchUnusedRecoveryCodesByEmail` (one query whether or not the email exists) → `findMatchingRecoveryCode`, which always compares against a full set, padded with `DUMMY_PASSWORD_HASH` (`src/lib/auth/dummy-hash.ts`, shared with `authorize()`), so timing reveals neither the account nor its count → `resetPasswordWithRecoveryCode`, which locks the users row first (the same lock order as `replaceRecoveryCodes`, so the two can't deadlock), then uses up the code and sets the password with a `session_version` bump in one statement → best-effort throttle clear (the code is already spent) → sign in, redirecting to `/dashboard`. An unknown email, a wrong code and a code a concurrent submit used first all get the same message. The last resort, with no codes and no other admin, is `pnpm run reset-password <email>` (`scripts/reset-password.ts`, logic in `scripts/reset-password/issue-reset-link.ts`): run with the database URL, it prints the same one-time reset link the Users page creates (via `createResetToken`, the account recorded as its own link's creator since `created_by` is required), with the base from `--url` or `AUTH_URL`.

Other admins are managed on `/dashboard/users` (`UsersManager`, `src/ui/users/users-manager.tsx`; linked from the admin menu, `src/ui/nav/admin-menu.tsx`). Every admin is equal (no roles). Invite, Create reset link and Remove each re-check the acting admin's current password under the login throttle (`inviteUser`/`createResetLink`/`removeUser`); Revoke on a pending invite doesn't. Invites and reset links are `user_tokens` rows (migration `0007`; SQL in the non-action `src/lib/users/tokens.ts`): a 256-bit base64url token from `generateUserToken()` (`src/lib/auth/user-token.ts`), stored only as its sha256, single use, expiring after `USER_TOKEN_TTL_HOURS` (72). The action returns the plain token once and the client builds the link (`OneTimeLink`) with the token in the URL fragment (`/invite#<token>`, `/reset-password#<token>`), so it never reaches a server log, Referer or analytics; those pages read it with `useLinkToken()`, which strips it from the address bar (keeping a per-tab `sessionStorage` copy so a reload still works), and submit it as a hidden field. A new reset link replaces the user's earlier one, and a reset link stores its target's `session_version` (migration `0009`) and works only while it still matches, so any password or email change voids it. Creating any token drops spent ones. The deliberately public `acceptInvite` and `resetPasswordWithLink` throttle like `recoverAccount` (window limit `invite:<ip>`/`reset:<ip>` → breached check → failure backoff on the same key), then turn away a dead link with a cheap `isUserTokenLive()` lookup before any bcrypt work, and on success clear both the IP key and the email's login backoff: `createInvitedUser()` (`src/lib/users/create.ts`) spends the token and inserts the user and its recovery codes in one statement (a taken email fails the whole statement, leaving the link unspent), then the form shows the codes as `/setup` does; `resetPasswordWithToken()` locks the users row first (the same lock order as `deleteUser()`, so the two can't deadlock), then spends the token and sets the password with a `session_version` bump, then signs in. Emails are unique case-insensitively (`idx_users_email_lower`, migration `0008`), so an invite or email change can't add a case variant of an existing one. Revoking an invite that was already used or revoked returns an error. `deleteUser()` (`src/lib/users/update.ts`) locks every users row, then deletes only another admin while the acting one still exists, so it can never remove the last admin (which `anyUserIsCreated()`'s memoization relies on), and the session check ends the removed admin's sessions; their tokens and codes cascade.

Rate limiting is Postgres-backed (`src/lib/auth/rate-limit.ts`; serverless has no shared memory). Logins go through `registerLoginAttempt`/`clearFailedLogins` (`login_attempts`, one row per key — usually an email, but any string works as one): 3 free failures, then exponential backoff capped at 15 minutes, surfaced as `CredentialsSignin` code `LOGIN_THROTTLED_CODE`. `createEmailSubscription` (failing open if the check errors), `recoverAccount` and `completeSetup` (failing closed) use `checkWindowLimit` (`rate_limit_events`, keyed by `getClientIp()`; a per-bucket `pg_advisory_xact_lock` serializes its count-and-record, so concurrent requests can't all slip under the limit). Post-login redirects go through `safeRedirectPath()` (`src/lib/auth/redirect.ts`), which keeps only a same-origin path.

First-run setup needs no env vars at import: a fresh instance's `instance_secrets` and `setup_code` rows are both written by every-deploy steps (see above) once Neon/Blob are connected and a build runs. While `users` is empty, the build log prints the live `setup_code` as a banner (`buildSetupCodeBanner()` in `src/lib/auth/setup-code.ts`, which also has the code's generation/hashing — Crockford Base32, 16 chars, 80 bits — and normalization, case/dash/space-insensitive); a kept-live code across rebuilds prints a note instead (`buildLiveSetupCodeNote()`), so a redeploy can't invalidate a code already in someone's hands. `/setup` (`src/app/setup/page.tsx`) is fully dynamic with no Suspense boundary — intentionally: a shell would flash before its own `hasUsers()` check either 404s it or renders the form, and nothing here benefits from partial prerendering. Once a user exists it 404s only for logged-out visitors: `completeSetup`'s sign-in cookie re-renders the page, so a signed-in visitor gets the same tree (`SetupForm isAccountCreated`) and the form keeps the recovery codes it's showing; a later visit redirects to `/dashboard` client-side. Its form posts to `completeSetup` (`src/lib/users/actions.ts`), which validates the account fields, caps attempts per client IP with `checkWindowLimit` (`setup:<ip>`, so the breached check that follows is bounded), runs the breached check (before the code throttle, so a rejected password doesn't count as a failed attempt), throttles failed codes per client IP (`setup:<ip>`, not one shared bucket, so a stranger's wrong guesses can't lock out the owner), checks the code (`verifySetupCode()` in `src/lib/auth/setup-code-check.ts`: expiry before a `timingSafeEqual` hash compare, so an expired code never leaks through a successful-looking compare), then calls `createFirstUser()` (`src/lib/users/create.ts`). That function atomically deletes the matching `setup_code` row and inserts the user in one statement (a data-modifying CTE) rather than checking `WHERE NOT EXISTS (SELECT 1 FROM users)` — Postgres serializes concurrent deletes of an existing row but not a check against an empty table, so only the CTE form stops two simultaneous submits from both creating an admin. `/setup` re-checks `hasUsers()` when `createFirstUser()` returns `false`, to tell "someone else already won" apart from "the code expired in the gap" and message accordingly. `scripts/setup.ts` no longer creates an admin at all — it stops after migrating, so this is the only code path that calls `createFirstUser()`. `completeSetup` signs the new admin in itself; a non-redirect sign-in failure after the account already exists returns a message pointing to `/login` rather than looking like setup failed.

### Site settings

One `site_settings` row: title, description, cover image (the `/about` OG fallback), `socialLinkIds` (the footer's links, max `MAX_SOCIAL_LINKS`) and `isEmailSubscribeEnabled` (whether the footer shows `EmailSubscribe`). The `Footer` renders nothing when it has neither links nor subscribe.

`navItems` (`nav_items` JSONB, migration `0010`) is the menubar: the shown items in order, each `{ path, label? }` with `path` from `navPaths` (`src/lib/site-settings/nav-paths.ts`, dependency-free so the client nav can import it) and a blank label meaning the default; hidden paths are left out, and `NULL` renders `DEFAULT_NAV_ITEMS`. It's edited in the settings form's Menu fieldset (`NavItemsFields`), whose rows the action checks before anything uploads. `Nav` reads it, then gives each shown path a status (`fetchNavItemStatus`, `src/ui/nav/nav-status.ts`), which the dashboard also uses for the fieldset's hints.

The site icon (`iconImageId`, picked like the cover image) is generated on save, after validation: `generateSiteIcons` (`src/lib/site-settings/icons.ts`, server-only; ICO packed by `ico.ts`) center-crops it (short edge ≥ `MIN_SHORT_EDGE`) into the five `SITE_ICON_FILES` at `iconKey(imageId, version, file)` (`icons/{imageId}/v{n}/{file}`), skipped when the stored `icon_image_id`/`icon_version` already match at `ICON_VERSION`. A custom icon is served only when both columns are set (`hasCustomIcon`; deleting the image clears just the id), at the stored version, else `public/default-icons/`. A save keeps a stored `icon_version` newer than `ICON_VERSION` rather than writing the older one (after a rollback, older code would otherwise point at files that version never wrote); it regenerates only when the stored version is older or the image changed. `siteIconUrls()` feeds the root layout's `icons` metadata, `src/app/manifest.ts` and the `/favicon.ico` redirect (`src/app/favicon.ico/route.ts`); there are no icon files in `src/app`, since file-convention icons override metadata. Bumping `ICON_VERSION` regenerates on the next save or `backfill-image-variants`; `copy-storage` copies `icons/`.

### Item pages and media

`ItemLayout` (`src/app/(item-pages)/item-layout.tsx`) renders every page item (events, releases, projects, and the default project at `/about`) with the same media rules. The cover image (`cover_image_id`, else the first of `image_ids`; in SQL, `resolve_cover_image_id()`/`build_cover_image_json()`, with `has_embed_code_type()` for the media icons, all defined in `src/seed/every-deploy.ts`) sits at the top of the article, and `images` never includes it. One embed code renders inline and 2+ go into an `EmbedCodesCarousel`. Images are counted with the cover: cover + 1 renders inline (`ImageInline`), 3+ go into an `ImagesCarousel` (cover excluded). Carousels sit below the article, embeds then images, before the page's `children`. Embed codes are a plain ordered `embed_code_ids` list on every domain (there is no featured embed code); list order decides what renders first.

Carousels share `Carousel`/`CarouselItem` (`src/ui/carousel/carousel.tsx`); a slide sized by its media's height uses `mediaSlideSize()` with the `media-slide` mixin (`src/ui/carousel/_carousel.scss`). Every image on an item page shares one `ImageLightbox` through `ImageGallery` (`src/ui/images/image-gallery.tsx`), in page order (cover, then the rest), so clicking the cover opens image 1 and navigation continues into the inline/carousel images. Clickable images use `GalleryImageFigure`; `ImagesCarousel`/`ImageInline` fall back to a gallery of just their own images outside a provider (`WithImageGallery`), and share the zoom-button styles in `src/ui/images/_image-button.scss`. Loading indicators use `Spinner` (`src/ui/spinner/spinner.tsx`; `label` for screen readers, `isCentered` to sit over a positioned parent), e.g. the lightbox while an image loads. "Download high-res" is offered only for `press`-type images (`isPressImage()`), and an images carousel is titled "Press images" only when every image in it is `press`, else "Images".

Page items in lists share their pieces through `src/ui/items/item-parts.tsx` (`ItemCoverImage`, `ItemTitle`, `itemCategory()`), used by both `ItemCard` and the table's `ItemsTableRow`; `FormattedItemDate` defaults to an event's venue timezone. `ItemCard` is also the projects carousel's slide (restyled in `projects-carousel.module.scss`, with `imageSize`/`isLazy` props for row-height sizing). Cards use a stretched title link (the whole card clicks through). Hovering anywhere on a card underlines only the title and darkens the image under an overlay; there is no full-card background. Links and buttons inside a card's text stay clickable above the stretched link. The card-shaped layouts (`ItemCard` in the projects carousel, the expanded `ItemsTable` rows on `/projects`) share their title/type/date spacing, "Unpublished" badge on the image's bottom-left corner (`isBadgeOnImage` / expanded rows; the title keeps a visually hidden "Unpublished" for screen readers, and a cover-less item gets a square placeholder to hold the badge) and hover (image overlay + title-text underline, no background fill) through `src/ui/items/_item-card.scss`; compact table rows keep their full-row hover fill. The expanded table (only `/projects`, via `isExpandedOnLoad`) is a justified layout, not a grid: each row sets `--aspect` from its cover (1 for the square placeholder) and grows in proportion to it, so cards per row vary and each row's images share one height; the cap is a max image height (`$media-height-max`), not a card width, and the basis/cap add the card's padding back, so a row's images always stay level. On mobile it drops to one full-width card per row (no cap). Both card layouts show the audio/video icons (`ItemMediaIcons`/`itemMedia()` in `item-parts.tsx`; `ItemCard` `isMediaIconsVisible`) beside the title, via the `title-with-media-icons` grid mixin. The overlay is the shared `image-overlay`/`image-overlay-visible` mixins in `src/ui/styles/_overlay.scss`, also used by the clickable images in `images-carousel.module.scss`. Don't `@use` `_interactions.scss` from a module for a mixin: it emits global rules. Captions everywhere (image/embed `figcaption`s, carousels, the lightbox bar) come from `src/ui/styles/_caption.scss`: the global `:where(figcaption)` rule uses `caption`, and a caption outside a figure uses `caption-text`. Don't restyle a caption per component.

### Images

The save action uploads each new file (`src/lib/images/upload.ts`: `uploadFile` reads the real format and size with `sharp`, issues the image id with `crypto.randomUUID()` and writes the original to `images/{id}.{ext}`; the row is then inserted with that id). Storage is behind one interface in `src/lib/storage/` (`put`/`delete`/`list`/`publicUrl`, with S3 and Vercel Blob adapters; `storageAdapter()` returns the active one, chosen by `STORAGE_PROVIDER` or, when unset, Blob if `BLOB_READ_WRITE_TOKEN` exists, else S3). `src/lib/storage/keys.ts` is the only place that knows a storage host, and is SDK-free so schemas and `next.config.ts` can import it. `imageSchema` derives `url` from `id` + `format` through `publicUrl`; rows with no `format` (saved before the storage copy) fall back to their stored `url`. An image's file never changes after upload: updates write only its details, a file submitted for an existing image is refused, and the edit form shows a saved image without replace/remove controls. `deleteImage` deletes the row, then the original. `pnpm run copy-storage --to <provider>` (`scripts/copy-storage.ts`) copies files between providers and renames older files to `images/{id}.{ext}`. Uploads go through the form's server action (body limit `SERVER_ACTION_BODY_SIZE_LIMIT`, under Vercel's ~4.5 MB cap), so new files are capped at `MAX_UPLOAD_FILE_SIZE` each and `MAX_UPLOAD_REQUEST_SIZE` per save (`src/lib/images/util.ts`), validated client-side and surfaced as a form error before upload starts. `readImage` also refuses formats other than JPEG/PNG/WebP/GIF, a short edge under `MIN_SHORT_EDGE`, and an aspect outside `MIN_ASPECT`–`MAX_ASPECT`. Images have a nullable `type` category (`press` | `documentation` | `flyer` | `artwork`, DB-constrained).

Each upload also gets WebP variants (`generateImageVariants` in `src/lib/images/variants.ts`, a server-only module rather than `'use server'`), one per `VARIANT_WIDTHS` width at `images/{id}_v{n}_{w}.webp` (`imageVariantKey`), never wider than the original, with animated GIF/WebP kept animated, plus a `blur_data_url` placeholder. The row records `variant_version`. A variant failure doesn't fail the save. `StoredImage` (`src/ui/images/stored-image.tsx`) is the `next/image` wrapper for uploaded images: with variants (`hasVariants()`) a per-component loader serves them straight from storage, and without them the optimizer resizes the original. `imageAspect()` trusts stored width/height only once variants exist; `ogImage()` picks the 1200 variant. Bumping `VARIANT_VERSION` and running `pnpm run backfill-image-variants` regenerates every image (versioned names get past year-long caches), then `--prune` removes old versions once a redeploy is live. `deleteImageFile` deletes the variants as well as the original.

### Embed codes

Beyond storing the pasted iframe/src, `src/lib/embed-codes/` resolves each embed's oEmbed metadata (title, thumbnail) server-side via `oembed.ts` (host-specific handling — e.g. unwrapping SoundCloud/Mixcloud's widget-wrapped `src` to the canonical content URL — since not every host sends CORS headers a browser fetch could rely on) and generates a cover image from it via `cover-image.ts` (using `sharp`, written through the active storage adapter); an embed code's `title` is always system-derived from `host`/`src` rather than user-editable. `preview-metadata.ts` exposes a client-callable `previewEmbedCodeMetadata()` for a live title/thumbnail preview while a form is still being filled in, deliberately skipping the storage upload so an abandoned form doesn't leave orphaned images.

### Mongo import

`scripts/migrate-mongo.ts` (helpers in `scripts/migrate-mongo/`: `transforms.ts`, `plan.ts`) is a one-off import of the old site's `mongoexport --jsonArray` files into Postgres. It never connects to Mongo. It records each created row in `legacy_ids` (`source`, `mongo_id` → `table_name`, `row_id`), so a re-run is a no-op. Like `copy-storage`, it uses direct SQL rather than server actions, never deletes or overwrites anything, and can't invalidate cache tags, so redeploy afterwards. A dry run writes a report to `<dir>/reports`.

### Testing

Jest + `next/jest` + jsdom, config in `jest.config.ts`, which pins `TZ=UTC` (matching CI/Vercel) and a fixed S3 storage env, so tests don't depend on a local `.env`, and ignores `.claude/` worktrees. Setup (`src/test/jest.setup.ts`) enables `jest-fetch-mock` and installs `AbortController`/`IntersectionObserver` mocks from `src/test/__mocks__/browser/`. `src/test/__mocks__/next/cache.ts` mocks `'use cache'`/`cacheTag`/`updateTag` for tests. Shared test helpers (`mockFile`, `formDataFromObject`) are in `src/test/helpers.ts`. Domain tests sit next to their source as `*.test.ts`/`*.test.tsx`. Tests that mock `sql` often assert on positional template params (`mockSql.mock.calls[n]?.[i]`), so adding or removing a column in an INSERT/UPDATE shifts those indexes.

## Code style

- Formatting is enforced by Prettier (`.prettierrc`): single quotes, no semicolons, no trailing commas, printWidth 70.
- ESLint enforces import sorting (`simple-import-sort`) and type-only imports (`consistent-type-imports`); unused vars/args/catch bindings prefixed with `_` are allowed.
- Path alias `@/*` maps to `src/*`.
- Boolean variables/fields/props use an `isX` prefix (e.g. `isSaved`, `isTouched`) rather than a bare adjective/participle (`saved`, `touched`).
